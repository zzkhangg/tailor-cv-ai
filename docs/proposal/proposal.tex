\section{Introduction}

\subsection{Background and motivation}
TailorCV is a web application that converts a text-based PDF resume into a consistent, job-targeted resume. Applicants frequently adapt the same resume for different roles, but manually identifying relevant evidence, reorganising content, and recreating a readable PDF is repetitive and error-prone. General-purpose generative AI can accelerate this work, yet unconstrained generation may invent skills, employers, dates, or achievements. TailorCV addresses this problem through a structured workflow that retains the source resume and validates AI selections against it.

\subsection{Objective and features}
The objective is to provide a responsive, end-to-end resume-tailoring workflow without requiring an account. The implemented MVP provides six user-facing functions: PDF upload and validation; structured extraction and confirmation; job-description storage; evidence-grounded AI tailoring; HTML preview with change and missing-requirement summaries; and ATS-friendly PDF download. It accepts selectable-text PDFs up to 5 MB and persists resumes, jobs, and tailoring runs. Tailored output requires user review and is not presented as a guaranteed ATS score.

\subsection{Traditional limitations and cloud benefits}
A desktop-only implementation ties processing and stored data to one machine, complicates updates, and cannot share capacity when demand changes. A single server also couples the user interface, document processing, AI integration, and database failure domains. Manual deployment creates downtime and inconsistent environments.

Containerised cloud services instead separate the public workflow from AI processing and persistence. Kubernetes can maintain replicas, replace failed Pods, distribute requests through Services, and perform rolling updates with rollback. Readiness probes prevent traffic reaching unavailable instances, while persistent storage separates database data from container lifetimes. ConfigMaps and Secrets keep deployment settings and credentials out of images. These capabilities make the service more scalable and resilient than a single manually managed host; they do not, by themselves, improve AI correctness.

\section{Technical solution}
The React 19 and TypeScript frontend is built with Vite and served by Nginx. It calls only the Java 21 Spring Boot \texttt{resume-service}, which validates PDFs, extracts text with PDFBox, owns the public REST API, persists data through Spring Data JPA and Flyway, and produces matching HTML/PDF output with Thymeleaf and OpenHTMLtoPDF. PostgreSQL 17 stores bounded original PDF bytes, extracted text, canonical JSON, job descriptions, and tailoring runs.

The stateless Python 3.12 FastAPI \texttt{ai-service} owns strict Pydantic parsing and tailoring contracts. Default extraction is conservative and rule-based. Optional OpenAI structured output uses bounded timeouts and schema validation. Tailoring selects source skills and experience bullets by index; Python then reconstructs the result from source data to reject unsupported claims. Provider failures are exposed only as sanitised errors. Docker Compose currently runs the four containers locally, with health and readiness checks covering service dependencies.

\section{Cloud deployment and cost}
The planned deployment uses Google Kubernetes Engine (GKE). Separate Deployments will run one frontend Pod and at least two Java and Python Pods. A public HTTP LoadBalancer Service will expose the frontend; Java and Python use private ClusterIP Services. Resource requests/limits and health probes will support scheduling and safe traffic routing. PostgreSQL will use a persistent-volume-backed Pod for the classroom demonstration; this economical design is not database high availability.

The browser never calls Python or PostgreSQL directly. Java orchestrates upload, persistence, tailoring, and export, while Python remains stateless and independently scalable. The assessment will demonstrate scaling, Service load balancing, Pod replacement, rolling update, and rollback. Current limitations are no authentication or OCR, dependence on PDF text order and an external model, and non-replicated PostgreSQL.
